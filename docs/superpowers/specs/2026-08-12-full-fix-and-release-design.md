# 全量修复与一次性发布设计

**日期**：2026-08-12
**范围**：Oxelia51（桌面 + 代理网关 + Go backend）、langfuse-token/web（Web 站点 + 云端配置）
**目标**：审查并完成当前工作区的全部未提交改动（含此前 Kimi 完成的 P0/P1/P2 修复），补齐必要修复，验证通过后一次性提交、推送、部署，并发布桌面 v0.1.6。

## 背景

当前 Oxelia51 工作区有 28 个已修改文件加若干未跟踪产物（`.verify/`、`desktop/sidecar/`、`scripts/preview-shots/`），涉及：

- 桌面 UI（`desktop/ui/src/**`）：总览布局、供应商/Agent 页、价格表、Agent 别名下钻。
- 代理网关（`proxy-gateway/**`）：路由归一、日期过滤、流式 duration、预算校验、限流落账。
- Go backend（`backend/internal/domain/auth/handler.go`）：登录相关。
- 部署配置（`deploy/nginx/snippets/security-headers.conf`）：安全头。
- `CHANGELOG.md`：已有未发布的 v0.1.6 小节。

这些改动来自本会话与另一 agent（Kimi）的连续迭代，尚未做过一次完整的跨仓库交叉验证，也未清理临时产物。用户要求："全部修复后一次性发布"——即所有已知问题必须在同一个发布窗口内处理完，不分阶段上线。

## 范围边界

**包含**：
1. Oxelia51 仓库当前 diff 的审查、去重、缺陷修复。
2. langfuse-token/web 仓库中与本次改动相关的安全头、登录文案、下载页限流等问题的审查与修复。
3. 全链路验证（后端测试、前端类型检查/构建、本地 E2E、生产只读探针）。
4. 按组件拆分提交、推送两个仓库。
5. 桌面 v0.1.6 三平台构建与 GitHub Release。
6. Web 侧 CI 触发、腾讯云部署、上线验证。

**不包含**（记录为遗留项，不在本轮修复）：
- 自定义供应商 SSRF 的连接时校验（DNS rebinding）——已有写入时校验，连接时校验是既有技术债，改动面大，不在本次范围。
- HSTS `includeSubDomains`——依赖 stats 子域上线，非本次触发因素，不强行捆绑。
- 任何本轮审查中新发现、但缺乏可复现证据或改动风险明显超出当前变更范围的问题——记录清单，不做猜测性修改。

## 修复与验证计划

### 阶段一：只读审查（不改代码）
逐文件走查 28 个已修改文件的 diff，确认：
- 每处改动都能追溯到一个已知问题（P0/P1/P2 清单或本轮新发现），没有遗留的调试代码、注释掉的逻辑、临时 print。
- 未跟踪产物（`.verify/`、`desktop/sidecar/`、`scripts/preview-shots/`）逐一判断去留：属于构建产物则加入 `.gitignore` 或删除，属于必要发布物（如 `desktop/sidecar/proxy.exe`）则保留并确认是最新构建。
- CHANGELOG v0.1.6 小节的描述与实际代码改动一致，不多不少。

产出：一份问题清单（确认无误 / 需要补充修复 / 需要清理）。

### 阶段二：补充修复（若阶段一发现问题）
仅修复阶段一确认的真实问题。修复原则与此前一致：小而聚焦，不引入无关重构，涉及行为变化的都补测试。

### 阶段三：验证门槛
发布前必须全部通过：

1. **Oxelia51 proxy-gateway**：`go test ./...` 全绿。
2. **Oxelia51 backend**（如有改动触达）：对应模块 `go test` 全绿。
3. **Oxelia51 desktop/ui**：`npx tsc --noEmit` 无错误，`npm run build` 成功。
4. **langfuse-token/web**：`pnpm --filter web run typecheck` 无错误；触达的模块跑对应测试。
5. **本地 E2E**（sidecar :17800 + UI :5173）：
   - 供应商/Agent 页日期切换（7/30/90 日）请求与展示正确联动。
   - Agent 别名设置后，下钻明细非空且数据正确。
   - 总览显示模式（全部/Token/成本）与三张排行卡片同步。
   - 模型名归一化（`model[1M]` 类变体）在排行与下钻中正确合并。
   - 429/非 2xx 响应不产生垃圾 token_events 记录。
   - 流式请求的 duration 落账为真实耗时而非固定 1ms。
6. **生产只读探针**：
   - Web 首页、下载页可达（HTTP 200）。
   - 下载页 GitHub Releases 信息正常拉取（若 GITHUB_TOKEN 已配置，确认未触发限流）。
   - 管理台可达性（不做写操作）。
7. **工作区 diff 最终审核**：确认无密钥、无数据库文件、无个人调试日志、无遗留截图误入待提交范围。

任一门槛未通过：停止后续阶段，回到修复循环，不进入提交/发布。

### 阶段四：提交
按逻辑边界拆分为独立提交（两个仓库分别提交）：

**Oxelia51**：
1. `fix(proxy-gateway): ...` —— 网关路由、统计、记账、限流相关修复 + 对应测试。
2. `fix(desktop): ...` —— 桌面 UI、Tauri sidecar 相关修复。
3. `docs(desktop): CHANGELOG v0.1.6 定稿`。

**langfuse-token**（仅当阶段一/二确认有实际代码改动时）：
4. `fix(web): ...` —— Web/安全头/登录文案等修复。

每个提交信息说明修复的问题与验证方式，不包含无关改动。

### 阶段五：发布
1. **推送**两个仓库对应分支。
2. **桌面端**：确认版本号，触发/执行三平台构建，创建 `v0.1.6` tag 与 GitHub Release，产物核对（Windows/macOS/Linux）。
3. **Web**：推送触发 CI 构建镜像 → 部署至腾讯云 → 上线后做只读验证（同阶段三第 6 项，换成部署后的生产地址）。
4. **发布后核对**：CHANGELOG 与 Release Notes 一致；下载页版本号与实际 Release 一致；生产服务健康检查通过。

### 失败处理

- 任一验证门槛失败 → 不推送、不发布，回到对应阶段修复。
- Web CI 构建失败或腾讯云部署失败 → 桌面 Release 同步暂缓（保持"一次性发布"的原子性：要么都上，要么都不上）。
- 生产上线后验证失败 → 立即执行回滚：Web 用旧 Docker 镜像/compose 备份；桌面 Release 若已发布但产物有问题，标记为 draft 或撤回，不误导用户下载。
- 所有生产操作前保留可回滚点：旧 sidecar 二进制备份（已存在 `proxy.exe.bak-p2fix`）、Web 部署前的镜像 tag、发布前的 Git 提交哈希。

## 关键权衡

- **为什么选"全部修复后一次性发布"而非分阶段**：用户明确要求版本叙事完整、一次到位；代价是任何环节失败都会阻塞整体发布，因此验证门槛设置得比分阶段发布更严格（阶段三覆盖后端/前端/E2E/生产探针四层）。
- **为什么遗留 SSRF 连接时校验和 HSTS**：这两项属于已知技术债，有明确的后续触发条件（分别是"改动面大需要专项设计"和"依赖 stats 子域上线"），强行塞进本轮会扩大范围、增加发布风险，不符合"聚焦当前已知问题"的原则。
- **为什么 Web 修复视情况而定**：如果阶段一审查确认 langfuse-token 相关文件（security-headers.conf、backend/handler.go）不需要额外改动（Kimi 已完成的部分已经足够），就不产生第 4 个提交，避免为了"凑一次性发布"而制造不必要的改动。

## 验收标准

- 阶段三全部验证项通过，有明确的执行记录（命令输出或 E2E 操作结果）。
- 两个仓库的提交历史清晰对应问题清单，无"杂项修复"式的模糊提交。
- 桌面 v0.1.6 GitHub Release 三平台产物齐全，下载页可正常展示。
- Web 生产环境部署后核心页面与下载信息可用。
- 遗留项（SSRF 连接时校验、HSTS）在 CHANGELOG 或 README 中有记录，不是被遗忘，而是被主动搁置。
